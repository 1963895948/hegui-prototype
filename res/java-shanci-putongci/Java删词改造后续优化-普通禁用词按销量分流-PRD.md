### 一、业务背景和价值

#### 1.业务背景

Java 删词改造后的流程以《QQJS-35837：java删词改造流程确认（责任人：袁效国）》为准，原文不改：

https://alidocs.dingtalk.com/i/nodes/Gl6Pm2Db8D3kB579t9yBwbnzJxLq0Ee4

原流程图里，数据在「是否禁售 = 否」且走到「普通禁用词」分支后，按近 365 天销量分流：

- 销量大于等于 0：进入人工处理（删词待处理列表）
- 销量小于 0：提交删词队列

销量为 0 的普通禁用词会进入销售人工列表，占用人工处理量。线上删词处理列表当前待处理约 **63.7 万**（截图统计 637035，以实际数为准），其中大量为近 365 天销量为 0 的普通禁用词。

本次只调整普通禁用词的销量判断，并对存量待处理数据按新规则重新触发删词流程。

#### 2.业务价值

- 近 365 天销量大于 0 的普通禁用词仍人工处理，避免自动删词影响有销量链接。
- 近 365 天销量小于等于 0 的普通禁用词改技术处理（提交删词队列），减少人工列表积压。
- 存量约 63.7 万待处理数据一并按新规则重跑，避免新旧规则并存。

#### 3.需求评级

- **P2**
- 可链接：《010 需求优先级识别制度（待执行）》

### 二、需求描述

#### 1. 需求背景

本次是 QQJS-35837 的后续优化：改普通禁用词销量分流，并重跑删词处理列表中的存量待处理数据。不改写基线文档。

#### 2. 目标用户

- 销售：处理分流后仍落在删词待处理列表中的有销量普通禁用词。
- 侵权禁售 / 系统：执行新分流，并对存量待处理数据重新触发删词流程。

#### 3. 核心目标

1. 普通禁用词：近 365 天销量 **大于 0** → 人工处理；**小于等于 0** → 技术处理。
2. 删词处理列表中现有待处理历史数据，按新规则 **重新触发删词流程**。

#### 4. 功能范围

做：

- 调整原流程图「普通禁用词 → 近 365 天销量」判断：大于 0 人工，小于等于 0 技术处理（提交删词队列）。
- 对删词处理列表中 **待处理** 状态的历史数据，按新规则重新进入删词流程并分流。
- 状态回写仍用基线文档的颜色和状态码。
- 新原型只展示本分流，不替换旧删词列表原型。

不做：

- 不修改 QQJS-35837 原文。
- 不改高危禁用词、商标词、SKU 禁售、店铺判断、每日删 listing 额度等原分支。
- 不改删词处理列表的查询条件、字段、批量操作和日志字段定义。
- 非「待处理」状态的历史数据不纳入本次重跑（如已保留、删词成功等）。

### 三、功能详细需求

#### 1 功能模块一：普通禁用词销量分流

##### 1.1 页面入口

无新菜单。分流在 Java 删词流程内部执行。

销售仍从删词处理列表处理人工数据。技术处理不进入该列表，进入删词队列。

原型：

https://1963895948.github.io/xiaoguo/qinquan-jinshou/java-shanci-putongci/index.html

##### 1.2 前置条件

1. 数据进入 Java 删词流程，且走到「普通禁用词」节点（未禁售，且非高危禁用词、非商标词主导分支）。
2. 销量字段使用 **近 365 天销量**（与删词处理列表「销量信息」中近 365 天销量一致）。

##### 1.3 功能描述

**与原流程差异**

| 近 365 天销量 | 原流程图 | 本需求 |
|---|---|---|
| 大于 0 | 人工处理 | 不变，人工处理 |
| 等于 0 | 人工处理 | 改为技术处理 |
| 小于 0 | 提交删词队列 | 不变，技术处理 |

**主流程**

1. listing 走到「普通禁用词」节点，读取近 365 天销量。
2. 销量大于 0：进入人工处理（删词待处理列表）；结束在人工节点时回写人工（5）。
3. 销量小于等于 0：技术处理，提交删词队列，不进入删词待处理列表；成功回写已删（1），失败沿用基线失败码与重试。

人工列表内的确认删词、删 listing、保留、回扫、日志，以及删词队列成功失败处理，均沿用 QQJS-35837。

#### 2 功能模块二：历史待处理数据重新触发

##### 2.1 页面入口

无新页面。由系统任务 / 技术侧触发重跑，不要求销售在列表上手动逐条重提。

##### 2.2 前置条件

1. 数据来源：删词处理列表中 **处理状态 = 待处理** 的数据。
2. 规模参考：上线前列表「待处理数量」约 **637035**（约 63.7 万），以重跑启动时的实际待处理数为准。
3. 新销量分流规则已上线或与重跑任务同时生效。

##### 2.3 功能描述

1. 对上述待处理数据 **重新触发删词流程**，按本需求新规则重新分流。
2. 重跑后：
   - 近 365 天销量大于 0，且仍命中普通禁用词分流：继续留在 / 进入删词待处理列表（人工处理）。
   - 近 365 天销量小于等于 0：走技术处理，提交删词队列，并从待处理人工列表中按流程结果移出（不再长期停留在待处理）。
3. 高危禁用词、商标词、禁售等仍走原分支，不因本次销量规则改道。
4. 重跑方式、批次、限流与删词队列吞吐：**待补充**（开发与业务按队列能力排期；目标是把存量待处理按新规则消化，而不是只改增量）。

#### 3 功能模块三：原型

##### 3.1 页面入口

独立原型，地址见 1.1。

##### 3.2 前置条件

示例数据，不接生产。

##### 3.3 功能描述

展示规则说明、分流试算、结果样例，并说明存量待处理数据需按新规则重跑。

### 四、风险描述

- 销量等于 0 改为自动提交删词队列，无法再在人工列表里先「保留」。
- 存量约 63.7 万待处理重跑会短时抬高删词队列压力，需控制批次与限流。
- 重跑期间列表待处理数量会快速变化，验收以规则正确性与重跑完成口径为准。

### 五、验收标准

#### 1 验收时间

默认：**需求上线后 5 个工作日内**验收完成。

#### 2 服务验收标准

1. 仅普通禁用词、近 365 天销量大于 0：进入删词待处理列表，不提交删词队列。
2. 仅普通禁用词、近 365 天销量等于 0：提交删词队列，不进入删词待处理列表。
3. 仅普通禁用词、近 365 天销量小于 0：提交删词队列（与原技术处理一致）。
4. 高危禁用词、商标词、SKU 禁售：仍走 QQJS-35837 原分支。
5. 对删词处理列表中待处理历史数据执行重新触发后：符合新规则的销量小于等于 0 数据进入技术处理；销量大于 0 的普通禁用词仍可留在人工列表。
6. QQJS-35837 原文未被本需求改写。
